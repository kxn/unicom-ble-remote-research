# 联通遥控器语音探索

2026-09-16 资料更新：[讯飞 / Realtek 编码、交互流程及官方工具线索](iflytek-realtek-sources.md)。新增候选尚未通过本机解码验证，以下原始实验结论保持不变。

日期：2026-09-15。用户确认现有机顶盒没有蓝牙，无法提供原主机语音握手抓包。后续使用已验证的 WinUSB 外接适配器与 Bumble，在 PC 上实验。

## 实测起点

- 见 [按键表](unicom-keymap.md) 与 [设备调查](unicom-ble-investigation.md)。
- 语音按下：HID F8（ATT value handle 0x003B）`82 03 01` 后补 17 个零；松开为 `82 03 00` 后补零。
- 同时有键盘报告 EA。订阅 HID 输入后仅按语音键，未收到连续音频。
- FB（0x0038）和 FA（0x003F）是 HID Output，具体用途未知；FC/F8/F9/04 的音频分工也未知。
- 初始阶段未发送语音业务写命令；本次新增主动实验结果见下文。FD00 用途未知，不能将它当作已确认的音频控制接口。

## 新资料与边界

[Realtek RTL8762D Voice RCU Design SPEC](https://www.realmcu.com/img/ipb/en_637441010047947270.pdf)，第 55–59 页：参考方案支持多种编码和语音流程。第 57 页 Figure 28 的 IFLYTEK 流程是按键通知后等待主机写 Start 0x01，再发送语音数据；Stop 为 0x00。

这支持“遥控器可能等待主机启动命令”的实验假设，但本机的 EA/F8 消息与该图的 0x3E 不同。图中未给出可直接对应本机的 Report ID、完整载荷和写入目标，不能直接宣布协议匹配，也不能把 0x01 随意写遍特征。

[RedRat 的 Nexus 遥控器调查](https://www.redrat.co.uk/products/rf-modules/ble-rcu/) 同样出现 F8/FA/FB，但方向、长度及其他报告不同，只能用于结构对照。

## 实验顺序

1. 准备独立语音捕获脚本，记录单调时间、通知 handle、原始字节、写请求/结果及连接事件；实验命令与结果一一对应。
2. 先复现短按/长按基线，必要时补测 FD02 的通知订阅（订阅不是语音启动命令），区分按键事件与连续数据。
3. 优先寻找接收端代码/SDK中与 F8:820301 和 FB/FA 输出对应的帧格式；有依据后，一次仅测试一个目标和一种握手。明确区分 ATT 写成功和设备业务响应。
4. 首个目标是可重复地启动/停止连续数据，不预设编码。每次采集限定时长，保存原始流。
5. 连续流出现后分别录制安静、固定短句、轻敲三种样本，比对速率、长度、序号及内容变化，再识别编码和重组帧。
6. 解码为 WAV，验证可听内容与实际说话一致，检查丢包和停止边界；成功后才将已验证协议移植到 CH582F。

## 主动实验结果：已启动数据流，解码未完成

证据：[本次原始事件](unicom-voice-evidence.jsonl)。运行环境 Bumble 0.0.234、WinUSB 外接棒，已配对加密，全部可通知特征已订阅。

| 实验 | 写入目标与载荷（ATT value，不含 Report ID） | 结果 |
| --- | --- | --- |
| 全通道订阅，不写业务命令 | FD02 CCCD 与全部 HID CCCD | FD02 主动通知 `10014b2a030204000203`；语音键仍只有按下/松开消息，无 FC 数据流 |
| FA 单字节候选 | 0x003F，按下写 `01`，松开写 `00` | 两次 ATT Write Response 成功；每次 F8 通知 `01`。无 FC 数据流。单字节响应含义未知 |
| FB 单字节候选 | 0x0038，按下写 `01`，松开写 `00` | FC（0x0034）连续输出，471 包，157 组，序号 1–157 |
| FB 重复实验 | 同上 | FC 再次连续输出，717 包，239 组，序号 158–396 |

两个 FB 实验都在 F8 的 `820301...` 通知后立即发写请求。第一轮启动到首个 FC 包约 70 ms。两轮都观察到松手及 `00` 写入后无更多 FC 包。

**边界：**尚未在持续按住时单独发送 `00`，因此还不能区分“松手自行停止”和“`00` 命令停止”的作用。两轮 FB 成功实验在同一连接内，且之前做过 FA 实验；尚需全新连接只订阅 HID、不先写 FA 的对照，确认最小启动条件。尚未确认 FD02 订阅是否必要。

### FC 分包

本次 1188 个 FC 包均为 20 字节，组成 396 个完整组，序号连续，无缺失分片。观察到的结构：

| 偏移 | 长度 | 观察 |
| --- | --- | --- |
| 0 | 2 | 小端组序号，同组相同，每组加 1；本次跨两轮录音继续递增 |
| 2 | 2 | 小端分片编号，依次 0、1、2 |
| 4 | 16 | 分片内容；第三片的尾部含重复字段，不能直接认定全部是音频 |

相邻组首包约相隔 20 ms；一组内三包通常紧邻到达。第三片内容的最后四字节重复第二片内容的最后四字节，第三片内容偏移 10–11 重复组序号。因此 48 字节整组内容直接拼接并不可靠。有效编码长度可能小于 48，40/38 等长度目前只是假设。

### 解码状态

离线尝试了 38 字节 iLBC、40 字节 G.726，以及给 38/40/48 字节候选载荷补 Opus TOC 的若干组合。解码器生成 WAV **不构成格式匹配证据**。用户试听了 40 字节载荷补 TOC B8 的候选，确认只有噪声、听不出话，该具体候选不成立。其他候选未通过可懂语音验证，不能报告已经确定编码、采样率或得到可用录音。

后续优先工作：隔离最小启动/停止条件；确认第三分片有效长度与可能的音频封装；再寻找芯片 SDK/接收端实现或验证编码候选。无需为这些 PC 实验刷 CH582F。

### 广电报批稿对照与尾部字段检查

重新核对上述广电报批稿附录 D（PDF 第 52–54 页）：SBC 必选，ADPCM、Opus、L2HC 可选；规定解码音频为 16 kHz、单声道、16 bit。这些是该稿要求，并非本机已确认参数。

- SBC 参数为 16 blocks、8 subbands、mono、loudness、bitpool 25，因此标准帧长 58 字节，头三个字节应为 `9C 31 19`。本次 396 组重组内容内没有该三字节连续特征；仍不能排除跨组、去头或不同参数。
- ADPCM 包定义了 PREDICT（2 字节小端）、PREDICTIDX（1 字节）、LENGTH（1 字节），位于 8 字节 SN/TS 后。应查找状态参数和解码后的连续性，不能用 G.726 候选代替 IMA ADPCM 检查。
- 本机每组去掉分片头后，拼接内容偏移 40 的小端 16 位字段均为 0–29（194/396 为零），偏移 42 的字段是组序号。这只是可能的状态/长度字段。
- 尝试将偏移 38 当作有符号 predictor、偏移 40 当作 IMA step index，用上一组状态解码下一组开头 36/38/40 字节，分别测试高/低半字节优先；每种组合的 395 次跨组检查均无末态匹配，甚至没有 index 匹配。该具体连续状态解释不成立，不排除其他位置、重置规则、打包方式或编码。
- 若每组只有 40 字节有效编码且代表 20 ms，则码率为 16 kbit/s；16 kHz 的常见 4-bit IMA ADPCM 则需要 64 kbit/s。须先确认组与音频时长的对应及有效长度，不能默认小米的 16 kHz IMA 解码参数可直接沿用。
