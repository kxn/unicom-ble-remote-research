# 下一步实验

更新：编码已确认为讯飞 ICO，原生实时解码和两段实机录音已通过用户试听，见 [实时通路](live-voice.md)。以下第 2、3 节保留为早期研究计划，已识别编码不再需要重做候选遍历；后续优先做停止条件、断连和丢包恢复。

> 2026-09-16 补充：控制指令面（FB 启停、FD00/FD02、厂商库中的 ListenAI 鉴权协议）与厂商库结论见[指令面](unicom-ble-commands.md)。

## 1. 先确定最小启动和停止条件

使用新的 BLE 连接，先订阅 HID，且不写 FA，测试语音按下后 FB=`01`。如果不能启动，逐个恢复已知环境条件，避免把多个条件同时改变。

已完成其中“不写 FA”对照：新连接订阅全部通知（仍包括 FD02），两轮 FB 录音成功。下一步仅需继续隔离 FD02 订阅。

随后分别测试：

- 持续按住语音键，主机定时发送 FB=`00`，确认主机能否独立停止。
- 松手时不发送 FB=`00`，观察遥控器是否自行结束以及尾包数量；实验仍须有超时清理。
- 去掉 FD02 订阅，确认它是否参与初始化。
- 连续两次录音、断开重连后录音，检查序号重置与状态继承。

当前脚本实现的是已执行的“按下启动、松手或 8 秒停止”实验。上述隔离实验需要先实现对应脚本选项，不能把目前的数据冒充为已做过。

## 2. 确定载荷边界

- 对齐 0/1/2 分片，检查跨组与跨录音边界。
- 第三片尾部的两个重复字段已验证；偏移 40 的 0–29 字段用途未知，可能是状态/长度等。
- 固定时长录制安静、持续纯音、短句，区分音频字节与帧元数据；纯音可用于验证采样率和时间比例。
- 比较连续流与间隔、连接参数，检查发送端是否存在缓冲或丢帧，不能只由通知间隔断言音频帧时长。

## 3. 用结构约束识别编码

- 新资料优先项：寻找“讯飞16倍压缩 / 微纳16倍压缩”的主机解码实现，并用已知样本核对标准 / 讯飞定制 Speex。来源、帧长及限制见 [资料补充](iflytek-realtek-sources.md)；40 字节与 16 倍压缩的吻合仍是假设。
- SBC：找同步字、完整参数、CRC 和连续帧边界；报批稿参数对应 `9C 31 19`、58 字节帧。当前尚未匹配。
- IMA ADPCM：寻找 predictor/index/length；按不同半字节顺序检查状态连续性。已试过的一种尾部状态解释失败，详见语音调查。
- Opus：先确认 TOC 是否存在、包边界和时长，再解码。给任意字节补 TOC 后解码器不报错不算证据。
- L2HC 或其他编码：保留为候选，需要更直接的 SDK/数据结构证据。四种广电候选并不穷尽本机可能采用的格式。

成功判据：多次录音能还原用户实际说出的不同句子，时长/音调正确，安静段合理，停止边界和丢包处理可解释。通过这些检查后，再考虑移植到其他硬件；移植是后续工作。
