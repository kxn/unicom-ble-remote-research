# 讯飞 / Realtek 语音格式资料补充

后续结果：本页是解码完成前的资料检索记录。编码现已确定为讯飞 ICO，纯 C 解码和实时录音均已验证；以 [语音调查](unicom-voice-investigation.md)和 [实机结果](live-voice.md)为准，以下未确定措辞仅反映当时状态。

检索与核对日期：2026-09-16。本文区分公开方案、样机实测和待验证推断；尚未找到与本机 FC 报文逐字节对应的源码，尚未解出可懂语音。

## 1. Realtek：交互流程与编码是两个配置项

来源：[Realtek S-Bee2 RCU Application Design SPEC](https://www.realmcu.com/img/ipb/en_637441010047947270.pdf)，第 13.4–13.5 节、文档页 55–61。

| 配置 | 文档列出的选项 |
| --- | --- |
| `VOICE_ENC_TYPE` | `SW_MSBC_ENC`、`SW_SBC_ENC`、`SW_IMA_ADPCM_ENC`、`SW_OPUS_ENC` |
| `VOICE_FLOW_SEL` | `IFLYTEK_VOICE_FLOW`、`HIDS_GOOGLE_VOICE_FLOW`、`ATV_GOOGLE_VOICE_FLOW`、`RTK_GATT_VOICE_FLOW` |

两者分别选择编码和交互流程，不能由 IFLYTEK 流程名称推出某一种编码，也不能认定所有组合都可用。

文档中的 IFLYTEK 流程：语音键按下上报 `0x3E`，主机写 `01` 后开始送音频；松手、处理尾部缓冲后上报 `00`，主机写 `00`。本机“主机写 01 才出现连续数据”的现象与它相似，但本机按键是 F8=`82 03 01/00`，尚未找到文档中的 FB/FC Report ID 或本机分片布局。

另外两条路径也不能混为一谈：ATV 使用 Google 服务并描述 134 字节通知；RTK GATT 使用自定义服务及 `0x3A40` 命令、`0x3A41` 数据特征。本机的 FD00/FD01/FD02 不能仅凭名称认定为这条 Realtek 语音路径。

[RTL8762D SDK 官方入口](https://www.realmcu.com/en/Resources/SDK/RTL8762D-Series)可作为后续查找入口。本轮未取得包含上述 RCU 配置及本机报文结构的完整实现；这不代表源码不存在，也不证明本机芯片是 Realtek。

## 2. 新线索：遥控器的“讯飞16倍压缩”

来源：青岛海信申请的 [CN110035308A《数据处理方法、设备和存储介质》](https://patents.google.com/patent/CN110035308A/zh)，2019-07-19 公开。

专利在遥控器语音场景中并列提到 SBC、微纳16倍压缩算法、讯飞16倍压缩算法，并提出通过配对阶段的广播自定义信息选择主机解码器。它没有公开后两种算法的实现、完整帧格式或可直接使用的编码类型编号映射。

**与本机的联系只是一个可检验的码率推断：**

```text
假设 PCM = 16000 Hz × 16 bit × 单声道
20 ms PCM = 640 字节
16 倍压缩后 = 40 字节
```

本机目前约每 20 ms 收到一组，组内前 40 字节是候选音频区域，数值恰好吻合。但“40 字节都是音频”“通知周期等于音频帧时长”“采样率为 16 kHz”均未确认。它值得优先寻找专用解码器，不能据此宣告编码已识别。

也不能把“讯飞16倍压缩”自动等同于 Speex、Realtek 的 IFLYTEK 流程或某个标准 codec。本机曾观察到的广播厂商数据也暂不赋予 codec 含义，需要真实编号映射及重新保存的广播证据。

## 3. 讯飞：标准 Speex 与定制 Speex 应分开验证

来源：[讯飞音频格式说明](https://www.xfyun.cn/doc/asr/voicedictation/Audio.html)、[讯飞大模型识别 Linux 文档](https://www.xfyun.cn/doc/spark/%E5%A4%A7%E6%A8%A1%E5%9E%8B%E8%AF%86%E5%88%ABLinux.html)。这些是语音服务/SDK 文档，**不是本遥控器 BLE 协议规范**。

按质量等级 0–10 排列的单帧字节数：

| 格式 | 8 kHz | 16 kHz |
| --- | --- | --- |
| 标准 Speex | 6, 10, 15, 20, 20, 28, 28, 38, 38, 46, 62 | 10, 15, 20, 25, 32, 42, 52, 60, 70, 86, 106 |
| 讯飞定制 Speex | 7, 11, 16, 21, 21, 29, 29, 39, 39, 47, 63 | 11, 16, 21, 26, 33, 43, 53, 61, 71, 87, 107 |

标准 8 kHz 的 38 字节帧与此前候选长度之一吻合；定制格式对应 39 字节。16 kHz 表中没有恰好 40 字节的档位。长度只能筛选候选，不能说明本机是 Speex，更不能因为差一个字节就随意添加/删除帧头。表中定制格式比标准多一字节，其字节含义和位置仍需验证。

### 可复现的官方工具线索

音频格式页面链接的 [speex_tools.zip](https://xfyun-doc.xfyun.cn/1551681433530034/speex_tools.zip)已下载并检查源文件，未执行其中的二进制程序。

```text
SHA-256: 9635e78144aa3809d4d3e208ca864370d86b2c3b778dda0c2264c9dd74884851
示例：linux_speex_tools_compile/Speex_test.c
接口：linux_speex_tools_compile/speex/include/speex/speex.h
```

示例调用 `SpeexEncode` / `SpeexDecode`；接口包含 `SpeexGetNbFrameLen`、`SpeexGetWbFrameLen`、`SpeexDetectFrameLen`，初始化参数区分窄带和宽带。示例分别以 320 / 640 字节 PCM 作为一帧。可用其产生已知输入样本，检查定制封装后再尝试原始数据。

目前检查的示例和头文件没有给出完整封装实现。头文件部分注释还混入 AMR 描述，不能把该注释当作此工具实际使用 AMR 的证据。下载包包含厂商库和使用限制；仓库只记录入口、哈希及分析，不重分发厂商二进制。

## 4. 与本机报文的对应关系仍有缺口

本机原始数据见 [语音调查](unicom-voice-investigation.md)和 [公开数据集](../data/README.md)：每个 FC 通知为 20 字节，前 4 字节为小端组序号、分片号；三个分片组成 48 字节内容，尾部存在重复序号及重复数据。

本轮没有找到同时解释以下字段的公开实现：

- F8 的 `82 03 01/00`，FB 的单字节启动命令，以及 FC 音频分片。
- 48 字节内容中偏移 40 的小整数、偏移 42 的重复序号、偏移 44 的重复数据。
- FD02 初始化消息 `10 01 4b 2a 03 02 04 00 02 03` 的字段含义。

因此，分包已识别与编码已识别是两件事；目前仍只完成前者。

## 5. 后续优先级

1. 查找“讯飞16倍压缩”“微纳16倍压缩”对应的电视/盒子主机解码库、接口和编码类型映射；优先有版本和来源的 SDK，避免仅凭文件名认定算法。
2. 离线建立标准 Speex 与讯飞工具的已知样本对照，检查帧长、封装、解码错误和时长，再测试有依据的候选边界。一次解码成功返回或生成 WAV 都不算识别成功。
3. 若取得 Realtek RCU 源码，沿 `VOICE_FLOW_SEL`、`VOICE_ENC_TYPE`、HID Report Map 和语音发送函数追踪实际字节布局；流程相似不替代布局一致。
4. 继续原计划的载荷边界、纯音时长和最小启动条件实验。只有多段实录能还原实际语句且时长/音调正确，才确认 codec。

本轮只补充资料，不修改原始报文，不把新候选写成实测结论。
