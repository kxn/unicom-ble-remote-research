# PC 实时语音通路

通路：WinUSB 蓝牙棒 → Bumble GATT → FC 分片重组 → 原生 ICO 解码器 → 16 kHz / 单声道 / 16-bit WAV。

## 构建与运行

在仓库根目录执行：

```powershell
.venv/Scripts/python.exe scripts/ico_decoder/build.py
.venv/Scripts/python.exe -m unittest discover -s tests -v
.venv/Scripts/python.exe scripts/voice_probe.py --record-voice
```

构建脚本使用原生 GCC/Clang，可通过 `--cc <编译器路径>` 指定；Windows 优先检测 `C:/msys64/mingw64/bin/gcc.exe`。参考源码逐个校验 SHA-256，DLL 和离线 demo 写入 `.local/ico/`。此通路不依赖厂商库或 ARM 模拟。

看到 `listening` 后，按住语音键说话，松手后等待 `audio_saved`，再开始下一段。默认主机在 8 秒停止，可用 `--max-record-seconds` 显式调整到 1–600 秒。若唤醒不能连接，需进入遥控器配对模式。

`--record-voice` 是明确启用语音业务写入的开关：每次按下 F8 语音键后向 FB 写 `01`，松手或超时写 `00`。默认不带该参数时，仍是原来的被动监听/手动排队实验模式（手动实验固定 8 秒上限）。录音模式只接受队列中的 `stop`，不混入 FA 实验。

```powershell
.venv/Scripts/python.exe scripts/queue_command.py stop
```

停止会完成当前录音的停止命令和尾包处理，然后断开。使用自定义 `--work-dir` 时，排队脚本也要指定同一个目录。

## 输出与判据

- `.local/session/voice-<时间>.jsonl`：原始通知、开始/停止写入、录音结果及连接事件。
- `.local/session/audio/ico_<时间>_<编号>.wav`：每次按键独立一段，开始时重置 ICO 状态。
- WAV 同名 `.json`：帧数、包数、时长、错误列表和 `valid`。

收到每组三个 20 字节 FC 通知后，核对分片顺序、连续序号、尾部重复字段；取重组内容前 40 字节，实时解出 320 个 PCM 样本。松手写停止后等待至少 300 ms 无新包，尾包等待最多 1 秒。

缺片、乱序、重复片、跳号、异常长度或尾部、断连及业务写入失败，会标记录音无效；保留已解出的部分 WAV 和原始日志，不做未经验证的丢包补偿。`valid` 仅表示收包/解码通路检查通过，最终仍需试听确认内容。没有收到音频的空录音也会标记无效。

## 回归范围

`tests/test_voice_audio.py` 用已保存的 396 组数据经过实时模块，逐字节对照原有离线 C demo；同时验证每轮状态重置、缺片/重复/乱序/异常长度、尾包不完整、空录音、序号跳变与 16-bit 回绕、尾部字段损坏。

原始数据不作修改，厂商二进制、配对密钥和新录音留在忽略目录。新录音需要单独试听；离线回归不替代真实设备测试。

## 超过 60 秒的连续录音实验

```powershell
.venv/Scripts/python.exe scripts/voice_probe.py --record-voice --max-record-seconds 120
```

目标是连续按住约 90 秒，超过此前用户观察到的小米 60 秒边界；主机 120 秒上限留出余量。按键期间不重复发启动命令、不主动重启录音，也不因暂时没有 FC 包而自动结束。

每 5 秒的 `recording_progress` 记录经过时间、完整帧数和 `seconds_without_fc`。`remote_mic_up` 只表示遥控器上报松键，不等于用户物理松手，必须与用户确认对照。`recording_end_requested` 及结果 JSON 的 `end_reason` 区分遥控器松键报告、主机时限、错误和会话结束。

判定不能仅看 WAV 文件长度：需核对首次/末次 FC 时间、组序号连续性、用户实际按住时间，以及停流前有无主机 `00` 或遥控器松键报告。即使通过 90 秒，也只证明至少支持这次时长，不证明没有更长时限。

实测结果与原始数据见 [连续录音实验](long-recording.md)：无刷新时两轮均为 20.7 秒；每 5 秒重发已知 `01` 后通过 40 秒测试，但一次音乐长录音在 59.84 秒远端断连，尚未验证超过 60 秒。

`--ignore-mic-up` 用于隔离自动松键报告的影响：只记录，不因此发送停止。`--refresh-start-seconds 5` 是显式启用的续时实验，默认 0（关闭），仅当最近 1 秒仍有 FC 时才重发已知启动值；也可选 10 秒。它们均要求 `--record-voice`，仍受主机时限、解码错误及会话停止约束。

## 回连修正与验证

旧探针每次连接都调用 `pair()`，且连接地址类型默认 RANDOM，而配对时未指定身份地址类型，Bumble 会优先分发控制器的 PUBLIC 身份地址。这使空口连接地址与登记的身份地址不一致，可能影响遥控器的回连过滤。此前多次出现连接后迅速以 reason 62 断开，不能将该现象简单归因于遥控器必须反复重新配对。

现统一使用控制器 PUBLIC 地址连接和分发身份信息。有保存的 LTK 时先调用 `encrypt()` 恢复加密，不重新配对；恢复失败不静默覆盖绑定。没有密钥才首次配对，明确需要重配时可使用 `--pair`。密钥仍在同一 `--work-dir` 的 `pairing-keys.json`，沿用既有命名空间以保留之前的绑定。

实机日志 `.local/session/voice-1789525810.jsonl`：用户仅按方向键、没有进入配对模式，发生 `connected` → `bond_restore_start` → `bond_restored`（encryption=1）→ `listening`，没有 `pair_start`。这验证了修正后可以复用原绑定回连；两项修正同时应用，尚未单独隔离其各自影响。

后续实验仍遇到过 reason 8/62 的短暂连接失败及一次连接等待卡住，重启探针后可复用密钥连接。这些稳定性问题尚未完整定位；成功恢复绑定不等于所有回连问题均已解决。断开清理失败现在单独记录，不覆盖最初的连接/加密错误。
